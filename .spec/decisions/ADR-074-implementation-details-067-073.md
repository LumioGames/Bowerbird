# ADR-074：ADR-067 至 ADR-073 的实现细则

状态：提议
日期：2026-11-27

## 背景

ADR-067 至 ADR-073 定了原则，每份末尾列了「实现时要定的」。本条是实现时按「先找最接近的已有决定，找不到就选更少人工步骤、更不容易丢数据的做法」（ADR-013）补的，待评审。

## 决策

**只在有了算不出来的信息时写 .bmeta（ADR-067）**
- 只被看见的文件在索引里有一个 GUID，与有 .bmeta 的资产同样能被搜索、查看、引用。第一次给它写信息时，.bmeta 用的就是这个 GUID。索引重建后它会换一个 GUID：磁盘上没有任何东西记着旧的。
- 索引的资产表多两列：`sidecar`（有没有 .bmeta）、`modified_by`（最后修改者）。索引格式版本升为 2，旧索引第一次打开时重建。
- 文件夹的默认阶段、默认校验、默认标签仍在第一次看见文件时算进索引里的那份元数据；写 .bmeta 时随之写入。之后改文件夹默认值，不影响已有资产（与原来「默认值只在认领时用一次」一致）。
- 管线从文件算出的东西（附属文件标记、按位置名配对的引用关系）：有 .bmeta 的资产照旧写进 .bmeta；只被看见的资产只记在索引里。
- 一个资产被别的资产的关系指向时，它的 .bmeta 随即写出，修改者记为这次写入的执行者。
- 第二种信息全部去掉之后，.bmeta 留着，不删。
- 只被看见的文件不记版本历史，内容变了就更新索引里的指纹。
- 一次扫描在走过某个文件夹之后，才有文件被写进去（上传、登记）：扫描收尾时先确认文件确实不在了，才把它从索引里忘掉或标成缺失；文件还在就留给下一次扫描。
- 只被看见的文件移入回收站后恢复，回来的只有文件，不生出 .bmeta（回收项记 `seen: true`）。
- 有 .bmeta 的资产被忽略规则命中：.bmeta 移入回收站、文件不动。磁盘上的 .bmeta 已经不在时，先用索引里的那份写出再移入回收站，信息不会只留在索引里被丢掉。规则仍命中时不让恢复，提示先改 .bbignore。回收站照旧按天数清理：误写一条很宽的忽略规则，要在清理之前改回来。
- 用路径写信息时，普通文件夹不是资产，包式资产里面的文件只能随整个包写，都会被拒绝。
- 只被看见的资产从文件里推算出的关系（位置名配对），在对方被忘掉时一起去掉并重新配对，文件在外部被挪动后会被重新找到。
- 「移出资产库」的接口是 `POST /assets/{id}/untrack`，命令是 `bb untrack`。移出后文件仍在，下一次扫描把它当成只被看见的文件。
- 已有资产库里只有 GUID 和指纹的 .bmeta 照旧保留，不自动清理。

**写入说出想要的结果（ADR-068）**
- 新接口 `POST /assets/apply`：一次最多 1 万项，每项用 `id` 或 `path` 指明资产，`dryRun` 只比较不写入。回答逐项列出 `changes`（字段、改之前、改之后）。
- 一项失败不影响其他项，都在回答里逐项说明。
- `path` 指向还没被扫描到的文件时，先把它看进索引再比较。
- 已有的关系再说一次时，不改它记着的对方版本：重新说一遍不等于「已复核」。
- 上传登记、按路径登记、`PATCH /assets/{id}`、批量修改的标签与阶段，都走同一个比较。上传时若请求里什么信息都没有，上传的文件只被看见。
- 命令行的清单是 JSONL，每行一项；也接受一个 JSON 数组；`-` 表示标准输入。清单里关系的对方可以写路径。

**命令免服务（ADR-069）**
- 命令按顺序找服务：
  1. `--server` / `BOWERBIRD_URL` 给出的；
  2. `bb serve` 写在 `<BOWERBIRD_HOME>/server.json` 里、进程还在且能应答的；
  3. 默认地址 `127.0.0.1:7420` 上能应答的。
- 后两种找到的服务，只在它打开了这条命令要用的资产库时才用（按 `--library`，或按工作目录所在的资产库文件夹判断）；否则命令自己打开资产库，绝不写进那个服务打开的另一个资产库。
- 命令自己打开资产库时，先等启动扫描完成，处理管线不运行（格式识别、缩略图都留给下次服务），在本进程的 127.0.0.1 随机端口起一个只供这条命令用的服务，做完就关。
- 要打开哪个资产库：`--library`，否则工作目录所在的资产库文件夹（没登记过就登记），否则这台电脑的默认资产库。
- 工作目录不在任何资产库里、也没给 `--library` 时，找到的服务照旧用它的默认资产库。
- 命令自己打开资产库时，每次请求都指名这个资产库：列出资产库会让服务为了访问控制打开它登记的每一个资产库。
- 同一个进程一次只自己打开一个资产库（MCP 的调用可能同时到达，后到的等前一个关掉）。另一个进程正占着时，命令最多等 10 秒。
- 锁是 `<本机数据目录>/libraries/<库>/writer.lock`，里面记进程号，用独占方式创建，两个进程不会同时拿到。进程还在、又不是自己时拒绝打开，报 `conflict`；进程不在了就接管。同一个进程里多次打开同一个资产库共用这把锁，最后一个关掉时才放开；打开失败时立刻放开。
- 锁放在本机数据目录里。同一台电脑上两个进程用了不同的 `BOWERBIRD_HOME`，就互相看不见对方的锁。
- MCP 服务的每一次调用都照此连接。
- 十万资产的库上命令开头对账的耗时没有量，性能基准里还没有这一项。

**出处写在 .bmeta 里（ADR-070）**
- 字段名 `provenance`，包含 `method`、`tool`、`plugin`、`prompt`、`params`、`batch`、`by`、`at`、`note`。元数据格式版本号 `bb` 不升：旧版本读到不认识的字段会原样保留。
- 输入写成来源或参考关系上的 `role`，关系同时记下对方当时的指纹。
- 批次号以 `bat_` 开头。插件的一次运行由内核生成，形如 `bat_<uuidv7>`。命令行一次登记多个文件、又给了出处时，由文件名和出处算出一个：同一条命令再跑一次，批次号不变，也就不会多写。
- 改出处时，没有再说批次号就保留原来的批次号；方式没变时保留原来的插件标识。
- 替换文件内容后，出处原样保留，不跟版本走：它说的是这个资产怎么来的，替换内容的人可以再说一遍。
- 旧资产库在全库扫描之后自动转换，文件缺失但 .bmeta 还在的资产也一起转换：
  - 每条记录的内容写进它的产出；
  - 记录的输入变成来源关系；
  - 多个产出共用一条记录时，记录号变成它们的批次号；
  - 切图的 `{ 产出: 区域 }` 拆给各自的产出；
  - 追加的备注合并进 `note`。
  - 所有资产都转换完、而且这次扫描没有被停下时，`.bowerbird/records/` 才改名为 `records-converted-<日期>`，不删；否则留到下一次全库扫描接着转换。
- 一批产出用搜索条件 `batch` 查（文本语法 `batch:`），不另设端点。

**能力只定义一次（ADR-071）**
- 定义放在 `@bowerbird/mcp` 的 `capabilities.ts`，因为这个包本来就是命令行与 MCP 共用的那一层，只依赖结构包，不依赖内核。
- HTTP 接口不从这份定义生成：接口是内核的边界，命令行与 MCP 是它上面的两种说法。
- 命令名就是能力名，MCP 工具名是 `bb_` 加能力名。参数在命令行写成 kebab-case，个别改了名字更好读（`--tag`、`--on`）。JSON 参数可以写 `@文件`。
- 能力表：search、get、trace、add、apply、tag、retarget、export、health、resolve、changes、rescan、rm、untrack、create、action、vocabulary。
- resolve、rm、untrack 不给 MCP。
- 原 MCP 的 `bb_register`、`bb_update`、`bb_fetch`、`bb_creators` 分别由 `bb_add`、`bb_apply` 加 `bb_retarget`、`bb_export`、`bb_create` 代替。
- 本地命令 init、serve、plugin、mcp 不在表里：它们不走接口。

**按最后修改者查（ADR-072）**
- 筛选字段 `modifiedBy`，文本语法 `editor:`，匹配规则与 `by` 相同。
- 摘要里有 .bmeta 时带 `metaPath`。
- `bb changes` 列出资产和要提交的文件。

**参考关系（ADR-073）**
- 标识 `reference`。
- 复制资产时与来源、引用一样跟着带走。
- 「与上游对比」暂时仍只认来源关系。

## 替代方案与否决理由

- **只被看见的文件用路径当标识，不给 GUID**：搜索、关系、接口里到处要区分两种标识，改动面大得多；而 GUID 在写 .bmeta 时直接沿用，Agent 搜到的标识一直有效。
- **命令发现没有服务时，自动在后台起一个服务**：ADR-069 已否决。
- **命令找到任何服务都直接用**：实现中实际碰到一台电脑上开着另一个资产库的服务，命令在别的资产库文件夹里运行时会读到那个服务的库。写入时会写错地方，所以加了「只用打开了这个资产库的服务」这一条。
