# 版本管理

Bowerbird 默认不保存旧版本的文件内容，只为每次内容变化留一条版本记录。需要查看、对比、恢复旧版本的使用者，安装一个版本插件即可。版本存储是一个扩展点，Lore 与 Git LFS 各由一个插件实现。第一期实现了版本记录、版本存储扩展点与没有插件时的界面；两个版本插件在第一期之后。

## 背景 / 目标

- 美术文件需要历史版本，尤其是对比“修改前后哪个更好”。
- 保留所有旧文件会让资产库体积成倍增长，不是每个使用者都需要。
- 已有成熟的工具专门解决大型二进制文件的版本问题，不应在内核里重新实现一套。
- 不装任何版本工具时，追溯功能仍要可用。

## 设计

### 两层能力

| 层 | 由谁提供 | 能力 |
|----|----------|------|
| 版本记录 | 内核，始终可用 | 每次内容变化的指纹、大小、时间、执行者、说明 |
| 版本内容 | 版本插件，可选 | 保存旧内容，按版本读取、对比、恢复 |

**版本记录为什么必须在内核里**：来源关系靠内容指纹判断“上游是否已更新”。这项追溯不依赖旧文件内容，只依赖指纹的历史，所以无论是否安装版本插件都能工作。

### 版本记录

- 资产内容每变化一次，元数据文件的 `versions` 追加一条。字段见 [`data-model.md`](data-model.md)。
- 触发来源：
  - 通过界面或接口替换内容、恢复旧版本；
  - 扫描器发现文件在外部被修改，执行者记为 `system:scanner`；
  - 重新定位到内容不同的文件、处理元数据冲突时保留另一份、对调重复身份。
- 只被看见、还没有元数据文件的文件不记版本历史（ADR-067、ADR-074）：索引里只有当前内容这一条，时间取文件的修改时间；内容变了，这一条换成新的。第一次写元数据文件时，这一条成为 v1。
- 恢复旧版本追加的一条带 `restoredFrom`，说明为「恢复为 vN」；恢复成与当前相同的内容也照样追加。
- 版本记录只追加，不删除。
- 版本以内容指纹标识。同一资产先后两次变回相同内容时，会有两条指纹相同的记录。

### 版本存储扩展点

接口以 `@bowerbird/plugin-sdk` 的 `server.ts` 为准；清单里用 `contributes.versionStore`（`{ id, displayName, ignore? }`）声明。

```ts
export interface VersionStore {
  id: string

  /** 资产库首次启用本插件时调用，建立所需的仓库结构 */
  init(library: { id: string; name: string; root: string }): Promise<void>

  /** 报告当前状态：是否就绪、是否有未提交的改动、远端是否可达 */
  status(): Promise<VersionStoreStatus>

  /**
   * 把一批变化保存为一个版本点。
   * changes 包含资产文件与其元数据文件的路径；meta 含执行者、说明、时间。
   */
  commit(changes: ChangeSet, meta: CommitMeta): Promise<VersionPoint>

  /** 某个路径的历史版本点，按时间倒序 */
  history(path: string, opts?: { limit?: number }): Promise<VersionPoint[]>

  /** 读取某个路径在某个版本点的内容 */
  read(path: string, point: VersionPointId): Promise<ReadableStream>

  /** 判断某个内容指纹对应的旧内容是否仍可读取 */
  has(path: string, hash: string): Promise<boolean>

  /** 与远端同步；没有远端的实现可以不提供 */
  sync?(): Promise<SyncResult>
}
```

**内核与版本插件的配合**

1. 每次写元数据文件、资产文件或文件夹设置都会交给 `commit`：登记、内容替换、恢复、修改元数据（标签、描述、阶段、出处、字段）、校验、增改与更换关系、确认上游复核、采纳或移除 AI 标签、手动缩略图、标签改名与合并、AI 富化、位置名配对、处理问题、移动、复制、移入回收站与恢复、移出资产库、文件夹设置与移动、创建包式资产、扫描器收进的外部改动。不在接口写操作里的写入（扫描器、管线）执行者记为 `system:scanner`。
2. 短时间内的多次改动合并为一次提交，避免产生过多版本点。合并窗口从第一次改动起算五秒。
3. 提交说明由内核生成：各操作名用分号连起来，后面写「（执行者：a、b）」，列出这段时间里改过东西的人；提交的执行者取第一个。
4. 元数据文件与资产文件一起提交，因此标签与关系的改动也有历史。
5. 版本记录里的内容指纹与版本点通过 `has` 与 `history` 对应：界面上某条版本记录能否预览，取决于插件能否读到那个指纹的内容。
6. 没有启用版本插件时，内核不收集这些改动。

**约束**

- 一个资产库同一时间只用一个版本插件：启用了多个时，内核只用第一个，并登记一条库级提示「同时启用了多个版本插件，只用「{名称}」，{其余} 不生效。停用多余的版本插件后这条提示会消失。」（问题类型沿用 `plugin-missing`，details 的 `kind` 为 `version-store-conflict`）。
- 更换版本插件不迁移历史。
- 版本插件自己的数据目录必须被 Bowerbird 的扫描器忽略。以点开头的目录（例如 `.git`、`.lore`）已被内置忽略规则覆盖；清单里 `versionStore.ignore` 声明的其他目录，内核在绑定与每次重载插件时加进扫描忽略规则。
- 版本插件不忽略缩略图。缩略图保存在资产库内的 `.bowerbird/cache/`，随资产库一起做版本管理与同步：一个人渲染过，其他人同步下来就有，不必重新渲染。

### 界面行为

| 功能 | 未安装版本插件 | 已安装版本插件 |
|------|----------------|----------------|
| 版本时间线 | 显示记录，不可预览；横幅「只记录了变化，没有保存旧文件」，并提供「选择版本插件…」（Lore、Git LFS） | 版本列表与选中版本的预览 |
| 版本对比 | 不可用，说明原因并给出安装指引 | 任意两个保存了内容的版本可对比 |
| 恢复旧版本 | 不可用 | 可用；旧内容写成一个新版本 |
| 替换内容后撤销 | 不可用，提示条不带撤销 | 可用；把上一版恢复为新的一版 |
| 上游已更新时查看变化 | 只显示“已更新”及时间，「对比上游的变化」置灰并说明「需要版本插件」 | 可对比上游的新旧版本 |

**元数据历史与历史关系图**：内核不记改动历史，元数据文件只保存当前状态。
- 版本页签只列内容的版本记录，关系图只显示当前的关系。
- 按版本看标签、物料阶段、校验与关系的改动，以及某个版本时的关系图，要由版本或历史插件提供「按版本取关系与元数据历史」的接口，现在的追溯接口没有这个能力（见待解决）。
- 安装了版本插件时，这些历史的来源是随资产文件一起提交的元数据文件。

**同步状态**：顶栏显示是否有未同步的改动，要用到 `status()`；外壳现在还不调用它。

**内容快照**：安装版本插件后，每条新的版本记录都对应一份当时内容的快照，查看器读取的就是它。安装之前留下的记录没有保存内容，界面上显示为「未保存内容」，不可预览，也不能参与对比。

**恢复**：恢复是一次内容替换，不改动已有记录。

1. 把旧版本的内容写回，追加一条新的版本记录，说明为“恢复为 vN”；界面上显示为例如「v3 恢复为 v1」。版本号 vN 是记录在 `versions` 中的先后序号，从 1 起。
2. 之后按替换内容处理：校验状态回到待审，以来源关系指向它的下游登记“上游已更新”。
3. 确认框说明会成为第几个版本、校验状态会回到待审、有多少个下游资产会被告知上游已更新。
4. 完成后可以撤销。恢复之后又反悔时，撤销是再做一次内容替换：把恢复之前的内容写回，再追加一条新的版本记录。已有的记录一条也不删除。

版本对比使用格式插件的对比视图，与对比两个不同资产是同一套界面。查看器通过统一的文件来源读取内容，不需要知道内容来自当前文件还是某个版本。

### Lore 插件

插件标识 `bowerbird.version-lore`，第一期之后优先实现。

**Lore 的相关特性**

- Epic Games 开源的版本控制系统，MIT 许可，面向含大型二进制文件的项目。
- 集中式、按内容寻址；大文件分块存储并在块级去重。
- 有零配置的本地模式，单个可执行文件，无外部依赖。
- 提供 JavaScript 等语言的接口绑定。
- 工作区可以只取用到的文件，历史留在服务端。
- 目前处于 1.0 之前，接口、协议与磁盘格式可能变化；官方承诺已写入的数据在后续版本可读。

**设计要点**

- 资产库目录即一个 Lore 工作区。插件随包携带或引导安装 Lore，并在本地模式下代为启动。
- 小团队共用时，Lore 服务端与 Bowerbird 服务部署在同一台机器上；其他人通过浏览器使用 Bowerbird，不需要各自安装 Lore。
- `commit` 对应一次 Lore 提交；`history` 与 `read` 通过 Lore 的接口按路径查询与读取。
- 使用者不接触任何版本控制命令。
- Lore 的提示性文件锁可以用来在界面上显示“某人正在编辑”，不作为第一版插件的内容。

**实现前必须验证的三件事**

1. 能否随 Bowerbird 一条命令启动本地模式。
2. 能否通过 JavaScript 接口完成提交，并在不展开整个工作区的情况下读出某个文件的历史内容。
3. 在一批真实的大文件上，速度与占用空间是否可以接受。

三项都通过才以 Lore 作为第一个版本插件；否则先做 Git LFS 插件。

### Git LFS 插件

插件标识 `bowerbird.version-git`，排在 Lore 插件之后。

**设计要点**

- 资产库目录即一个 Git 仓库。插件在初始化时写入 `.gitattributes`，把二进制格式交给 LFS，元数据文件（`.bmeta`）与文档按普通文本管理。
- `commit` 对应一次 Git 提交；`history` 用按路径的日志查询；`read` 读取对应提交里的文件，必要时先取回 LFS 对象。
- `sync` 对应推送与拉取。远端冲突时不自动合并，登记为问题交给人处理。

**需要向使用者说明的限制**

- LFS 对每个版本保存完整文件，不做差量，不会减少总体积；它的作用是把历史放在服务器上。
- 需要一个支持 LFS 的远端仓库才能在多台机器之间同步。
- 资产库不能放在云盘同步目录里，Git 仓库在其中容易损坏。

### 不做的方案

- 内核不内置任何保存旧文件的机制。
- 不提供按策略自动清理旧版本的功能；保留多少历史由所选的版本工具决定。

## 待解决

- Lore 的三项验证尚未进行；Lore 与 Git LFS 两个插件都还没有做。外壳「选择版本插件…」里列出的两个包现在装不上。
- 版本插件的远端同步冲突如何在界面上呈现，留给插件设计。
- 资产库很大、只同步其中一部分时，指向没同步下来的资产的关系如何显示，未定；现在按断链显示。
- 按版本取关系与元数据历史的接口：版本页签的「标签与关系」筛选与历史关系图都靠它，需要版本或历史插件提供。
- 版本存储的同步状态在顶栏的显示，以及 `versionStore.ignore` 加入忽略规则。
