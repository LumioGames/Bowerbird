# ADR-052：管线、缓存与任务细则——阶段记账、缓存键与清理、渲染租约与重试、任务事件、创建与动作任务、插件位置、文件监听的规模

状态：提议
日期：2026-11-26

## 背景

pipeline-and-cache.md 规定了阶段、任务状态、缓存键的组成和「定期清理」，但没写到能照着实现的程度。实现与审查时补了这些细节：
- 怎么知道一个阶段该不该重做；
- 别的机器同步来的渲染结果能不能直接用；
- 浏览器领走的渲染任务交回时内容已经变了怎么办；
- 创建任务失败要不要自动重试；
- 插件动作怎么跑。

另外，原来用 chokidar 监听整个资产库，在 macOS 上每个文件占一个句柄，十万个资产时进程句柄耗尽。

本条把第一期实现时自行定下的做法合并成文（ADR-013），待评审。

## 决策

**阶段记账与启动时找过期工作**
- 每个资产的每个阶段做完或跳过时，在 `pipeline_stages` 记一行：资产、阶段、内容指纹、引用、插件@版本、时间。
- 启动时：
  - 进行中的处理任务回到排队，退避计时与渲染租约清掉；
  - 排队中或进行中的创建、动作任务记为失败，原因「服务重启，任务中断」。
- 然后找过期工作，按积压优先级排队：

  | 情况 | 重做范围 |
  |------|----------|
  | 格式插件版本变了 | 这一阶段与之后的阶段 |
  | 富化、校验、搜索插件这一组变了（升级、新增、移除） | 对所有资产重做这一阶段 |
  | 插件没了 | 从识别开始 |
  | 未知格式的文件现在有插件能读了 | 识别 |
  | 内容指纹与识别时不同 | 全部阶段 |
  | 从没处理过 | 全部阶段 |

- 引用的文件内容变了的，在后台重做派生、缩略图、摘要。
- 富化、校验、入索引三个阶段记下的「插件@版本」是做的时候启用着的整组插件，跳过时也记；处理过、但还没有这一阶段记录的资产也补做。
- 运行中启用、停用、安装、更新、删除插件后，同样找一遍过期工作。
- 搜索插件的索引被清空（`clearProviders()`）后，对所有资产重做入索引。

**缓存键**
- 缓存键是下面四行用换行连起来后的 SHA-256：
  1. 内容指纹；
  2. 排序后的引用，每项写成 `位置名=指纹`，缺失的写 `位置名=missing:<GUID>`；
  3. `插件标识@版本`；
  4. `阶段:变体@参数版本`。
- 文件放在 `<阶段>/<键的前两位>/<键>.<后缀>`。
- 摘要文字也缓存：放在 `summary` 阶段、`text` 变体，内容为 `{ "text": … }`。读摘要时先用它，没有时才现场生成。
- 插件通过缓存写入器写的文件放在 `<阶段>/plugins/<插件标识>/<GUID>-<指纹前 8 位>/<名字>`。
- 缓存文件经 `library` 模块写入。

**缓存清理**
- 已登记的缓存文件，所属资产已不存在：删除。回收站里的资产保留它的缓存。
- 没登记、但在管线自己目录结构里的文件，分两种：
  - 现存或回收站里的资产能推出这个键：直接登记使用，同时完成等它的渲染任务。这就是别的机器同步来的渲染结果。
  - 推不出这个键：超过宽限期才删。
- 宽限期：定时清理 24 小时，手动清理 10 分钟，临时文件 1 小时。
- 只碰自己的目录结构，别的文件一概不动；「清空缓存」也只删自己的目录结构。
- 定时清理每 24 小时一次。

**渲染租约与重试**
- 浏览器领取渲染任务时，租约 120 秒，并记下当时的内容指纹、引用与插件@版本。
- 交回时：
  - 任务已经重排，或没有租约：静默丢弃；
  - 记下的指纹对不上：丢弃，清掉租约，按近期优先级重排。
- 浏览器渲染失败时，错误带 `retryable`，没带的按可重试处理：
  - 可重试的自动重试 3 次，间隔 2 秒、15 秒、60 秒；之后记失败并登记 `pipeline-failed`；
  - 不可重试的立即失败。
- 服务端处理阶段的重试间隔与次数相同。

**`job.updated` 的发送范围**
- 按资产库发送。
- 处理任务：等渲染、取消、最终失败、重试之后成功时发。首次就成功、排队、开始运行时不发，免得十万个资产入库时刷屏。
- 渲染任务：从缓存补上、安排重试、失败、完成时发。
- 创建与动作任务：开始、每次 `progress()`、每登记一个产出、结束时都发。

**创建任务**
- 不自动重试。失败时标为可重试，人可以手动重试，用同样的参数。
- 取消后状态为 `cancelled`；之后再调 `register` 会抛出「任务已取消」。
- 服务重启时，进行中的记为失败。
- 插件没带生产记录时，内核补一条：`method` 为 `<插件标识>/<创建方式标识>`，带上参数与输入资产及其角色。插件的记录没写输入时，内核补上。

**动作任务**
- 插件动作作为 `kind: 'action'` 的任务，由管线的 `startAction` 运行。重试与取消与其他任务相同。
- 一次运行的全部产出共用一条生产记录。

**标识**
- 创建方式与动作的标识对外一律写成 `<插件标识>:<标识>`，任务的 `creator` 字段也一样。

**插件不得放在资产库内**
- 安装时，路径落在任何已登记或已打开的资产库里：拒绝。
- 本机配置里这样的路径安装，在发现时标为失败，不加载（ADR-012）。

**文件监听的规模上限**
- 不再用 chokidar，改用 Node.js 自带的 `fs.watch`。
- macOS 与 Windows：在根目录上用系统的递归监听，整库一个句柄。
- 其他系统（Linux）：
  - 逐个文件夹监听，`.bowerbird` 与被忽略的文件夹不监听；
  - 文件夹超过 2 万个时不监听；
  - 运行中超过上限时关掉全部监听；
  - 新出现的子文件夹单独加监听。
- 监听不了或关掉时，靠定时扫描发现变化（默认每 10 分钟）。
- 资产库信息带 `watch: { enabled, mode, reason?, dirs? }`，说明是否在监听、为什么没有。
- 监听事件只给路径，扫描器自己判断文件是否稳定：修改时间早于 2 秒算稳定，否则 2.2 秒后再看。

## 替代方案与否决理由

- **每次启动全部重做**：十万个资产要几个小时。
- **别的机器同步来的渲染结果一律当垃圾清掉**：违反 ADR-025「缩略图随资产库同步」，每台机器都要重新渲染一遍。
- **渲染交回时不核对内容**：领取之后文件被替换了，旧内容的缩略图会挂在新内容上。
- **创建任务失败也自动重试**：创建可能调用收费的外部服务，重试要人决定。
- **继续用 chokidar**：在 macOS 上句柄数随文件数增长，大库会耗尽句柄。
