# ADR-007：版本管理为可选插件，内核只记版本记录

状态：Accepted
日期：2026-11-25

## 背景

美术文件需要历史版本，尤其是对比修改前后的两个版本。但保留全部旧文件会让资产库体积成倍增长，且不是所有使用者都需要。讨论中先后考虑过只记记录、内核内置版本库、Git LFS、Epic 开源的 Lore。

## 决策

- 默认不带版本管理：内核只为每次内容变化记一条版本记录（内容指纹、大小、时间、执行者、说明），不保存旧文件内容。
- 版本记录留在内核里，因为“上游已更新”的追溯依赖内容指纹的历史，不依赖旧文件内容。
- 保存、读取、对比、恢复旧版本内容由版本插件提供。版本存储是一个扩展点。
- 计划提供两个版本插件：Lore 与 Git LFS。使用者自行选择，一个资产库同一时间只启用一个。
- 第一期只定义扩展点与默认行为。之后先做 Lore 插件，前提是通过三项验证（能随 Bowerbird 一条命令启动本地模式；能通过 JavaScript 接口提交并读取历史内容；真实大文件上的速度与空间可接受）；验证不通过则先做 Git LFS 插件。
- 版本对比使用格式插件的对比视图，与对比两个不同资产是同一套界面。

## 替代方案与否决理由

- **只记版本记录，不提供任何保留旧内容的途径**：最省空间，但无法对比两个版本，不满足美术评审的需要。
- **内核内置版本库（旧文件移入库内的版本目录，按内容指纹去重，并按策略自动清理）**：无外部依赖，但等于自己实现一套简化的版本控制，且只有整文件去重。已有专门的工具把这件事做得更好。
- **以 Git LFS 作为地基**：成熟，但每个版本保存完整文件，不减少体积；需要支持 LFS 的远端；Git 仓库放在云盘或 NAS 同步目录里容易损坏；与“资产库是任意本地文件夹”冲突。
- **以 Lore 作为地基**：分块去重、有零配置本地模式和 JavaScript 接口、MIT 许可，是最契合的工具；但目前处于 1.0 之前，接口与磁盘格式可能变化，不适合作为所有使用者的强制依赖。
- **依赖存储设备自带的快照（NAS 快照、网盘历史版本）**：零开发成本，但 Bowerbird 看不到这些版本，无法在界面里预览和对比。
- **在支持写时复制的文件系统上自动留快照以防外部覆盖**：只在部分文件系统上有效，增加复杂度，随内置版本库一并放弃。

## 兼容影响

- knowledge/features/versioning.md 定义版本记录、扩展点与两个插件的设计要点。
- knowledge/features/data-model.md 的版本记录字段。
- knowledge/features/web-shell.md 的版本时间线在有无插件时的不同表现。
- 直接在文件夹里覆盖文件时，若未安装版本插件，旧内容无法找回；这一点需要在使用文档中说明。
