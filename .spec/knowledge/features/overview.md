# Bowerbird 总览

Bowerbird 是一个网页版的游戏资产管理器，源码公开（ADR-058）。它把图片、视频、音频、3D 模型（含其中的动画）、文档等资产放进一个磁盘文件夹统一管理，让人可以浏览、预览、校验和追溯，也让 Agent 可以按标签和语义检索并取用。

## 背景 / 目标

**要解决的问题**

- 游戏资产分散在各处，没有统一的标签、预览和检索入口。
- 资产之间的生产关系没有记录：一个模型来自哪张原画、哪段提示词，一张原型稿切出了哪些小图，事后无从追溯。
- 生产过程中的物料和游戏实际使用的物料混在一起，人和 Agent 都分不清哪个是成品。
- Agent 参与生产后，需要一个它能直接检索、登记和取用资产的接口。

**目标**

| 编号 | 目标 |
|------|------|
| G1 | 一个磁盘文件夹就是资产库，是资产的唯一真值；本地盘、NAS、云盘、Docker 卷都只当本地目录读写 |
| G2 | 每个资产有永久身份（GUID），改名和移动不影响引用 |
| G3 | 记录资产间的来源、参考、引用、归属关系与资产的出处，可以向上游和下游追溯 |
| G4 | 区分参考素材、生产物料、运行时物料，并记录校验状态 |
| G5 | 在浏览器里预览各类资产，3D 模型支持 PBR、通道、分屏对比和环境光照 |
| G6 | 网页和 Agent 共用一套接口；Agent 能搜索、追溯、登记、取用 |
| G7 | 格式支持、搜索、AI、创建资产、版本管理、访问控制都是插件，内核不认识任何具体格式 |
| G8 | 一条命令启动，不依赖外部服务；面向小团队自托管 |

**非目标**

- 内核不做登录、账号、权限和多租户。这些能力由访问控制插件提供：内核在每个接口请求进入时询问它（ADR-049），第一期没有带这样的插件。内核自己只校验主机头与来源头。
- 内核不记标签、关系、校验的改动历史，元数据文件只保存当前状态。需要历史的团队安装历史插件；第一期没有这样的插件。
- 不替代游戏引擎内的最终效果验收。网页查看器用于检查资产是否合乎制作规范。
- 不在内核里绑定任何 AI 服务或版本控制系统。
- 不在服务器上渲染。需要渲染的缩略图由打开页面的浏览器生成，没有人打开页面时不生成。
- 第一期不做桌面应用和手机应用。

## 设计

### 设计原则

1. **文件夹即真值**。资产库是一个格式公开的普通文件夹，离开 Bowerbird 仍然可读；索引和缓存都可以从它重建。
2. **内核不认识格式**。内核只管资产、关系、任务和插件；所有后缀格式的识别、预览、缩略图由格式插件提供。
3. **内置与第三方同一套接口**。随内核发布的插件不享有任何私有通道。
4. **永不修改原始文件**。内核与插件在读取、预览、处理资产时不改资产文件，只写元数据文件、库级数据和缓存。上传、登记与替换内容会写入资产文件，它们是使用者发起的写入。
5. **问题显式暴露**。断链、缺失、重复身份、上游已更新，一律列出并提示，不静默修复。
6. **人和 Agent 走同一条路**。网页外壳不调用任何 Agent 调不到的接口。
7. **流程尽量不要人工步骤**。能自动识别、推断的就自动完成，结果给出可信度；人只在结果明显不对时介入，不设计要求人工标注的步骤。

### 整体架构

系统由四层组成，自上而下：

| 层 | 组成 | 职责 |
|----|------|------|
| 使用者 | 浏览器、Agent（MCP、命令行、HTTP） | 发起操作 |
| 接口 | HTTP API、事件流 | 唯一入口，网页与 Agent 共用 |
| 内核 | 资产库读写、数据模型、扫描对账、任务管线、索引与查询、插件宿主 | 与格式无关的通用能力 |
| 插件 | 格式、搜索、富化、入库来源、创建、校验、模板、动作、界面、版本存储、关系类型、访问控制 | 一切与具体格式、AI、团队规范、登录相关的能力 |

网页外壳是单独构建的静态页面，由服务进程托管，只通过 HTTP API 工作，与 Agent 用同一套接口。

内核之下是磁盘：资产库文件夹保存真值，本机数据目录保存可重建的索引。

### 进程与部署形态

- **单进程服务**：一个 Node.js 进程同时提供 HTTP API、构建好的网页外壳、扫描器和任务管线。索引用内嵌的 SQLite，不需要独立数据库。
- **不开服务也能用命令**：服务是用来看和加速的。服务没开时，命令自己打开资产库，读写完就退出；同一时刻只有一个进程在写（ADR-069）。
- **本机使用**：`bb serve <资产库目录>` 启动后在浏览器打开，默认只监听 `127.0.0.1`，端口 `7420`。
- **小团队共用**：把同一个进程部署在一台放得下资产库的机器上（例如 NAS 上的 Docker），其他人用浏览器访问。需要显式指定监听地址，详见 [`api-and-agent.md`](api-and-agent.md) 的安全一节。第一期没有访问控制插件：能访问到这个地址的人，能用的功能与本机相同，包括安装插件；只有打开文件、在文件夹中显示、导出到目录这几个本机动作限本机。
- **多个资产库**：一个资产库是一个根文件夹。一个 Bowerbird 可以登记多个资产库，在界面上切换；切换只影响当前浏览器，不影响其他人正在看的页面。

**使用方式**

- 只看的人用浏览器访问。
- 要在本机改文件的人，把整个资产库文件夹同步到本机，并在本机启动 Bowerbird。
- 同步用什么工具不由 Bowerbird 管。版本插件在第一期之后。

### 分期

**第一期**交付一个可用的通用资产管理内核，已经实现：

- 内核全部模块。
- 网页外壳全部页面。
- 内置插件：图片、视频、音频、3D 模型、文档、关键词搜索。3D 模型支持 GLB、glTF、FBX。
- 模型对照四视图：在对比页里并排、卷帘、叠加。
- Agent 接口：MCP 与命令行。
- 给以后的插件留的位置：创建与动作插件要用的登记通道与出处格式已经做好；访问控制已在每个接口请求上接好；改动通知只定了接口，内核还不调用。第一期不带创建插件、访问控制插件、历史插件与版本插件。

**第一期之后**按顺序：

1. 语义搜索与 AI 打标插件。
2. 版本插件，先 Lore，后 Git LFS。
3. 模板插件与规则校验插件，承载团队自己的制作规范。
4. PSD、Spine、序列帧、特效预览、引擎对接、桌面与手机应用。

创建插件（例如 AI 生图、由四视图生成模型）、访问控制插件（登录）、历史插件（改动历史）也在第一期之后，先后顺序未定。

第一期先做了完整的交互原型（`design/prototype/`），再按本目录的文档实现。代码在 `packages/` 与 `plugins/`，样例资产库在 `fixtures/`；实现中补的决定见 ADR-027 至 ADR-057，之后的改动见 ADR-058 起；仓库在 `github.com/LumioGames/Bowerbird`（ADR-057）。

### 术语表

| 术语 | 含义 |
|------|------|
| 资产库 | 一个根文件夹，Bowerbird 管理的全部内容所在；一个 Bowerbird 可以登记多个资产库 |
| 资产 | 资产库里一个可独立预览的文件，或一个作为整体的文件夹（包式资产） |
| GUID | 资产的身份，文件第一次被看见时生成；写进元数据文件后永久不变，不随改名、移动、内容变化而变 |
| 内容指纹 | 文件内容的哈希，表示“是哪一版内容” |
| 元数据文件 | 与资产同名、加 `.bmeta` 后缀的文件，保存该资产的 GUID 与全部算不出来的信息，例如 `chest.glb` 旁边的 `chest.glb.bmeta`；有人给资产记下信息后才有（ADR-067） |
| 只被看见的文件 | 扫描器看见、还没有人给它记下信息的文件；只在索引里，没有元数据文件 |
| 登记 | 有人或 Agent 给一个文件记下了算不出来的信息；扫描器看见文件不叫登记 |
| 物料阶段 | 参考素材、生产物料、运行时物料三者之一 |
| 校验状态 | 待审、通过、打回、免审四者之一；通过还是打回只由人决定 |
| 自动检查 | 校验插件对资产做的检查，结果只显示，不改变校验状态；内置只有模型尺寸对照一条 |
| 关系 | 资产之间带类型的有向关联，内置来源、参考、引用、归属四种；关系的对方可以更换 |
| 位置名 | 资产文件里写着的引用名，例如模型文件里的贴图文件名；它只表示“这里有一个位置”，位置对应哪个资产记在元数据文件的关系里（字段 `slot`） |
| 出处 | 资产是怎么做出来的：方式、工具、提示词、参数、批次号、执行者；写在资产自己的元数据文件里，可以改；输入由来源与参考关系表达（ADR-070） |
| 批次号 | 同一次产出的多个资产在出处里共用的标识，形如 `bat_…` |
| 创建 | 一类扩展点。插件声明创建方式，由人或 Agent 发起，产出经内核登记成为资产 |
| 版本记录 | 资产内容每次变化留下的一条记录，不含旧文件内容 |
| 执行者 | 做出某次操作的人或 Agent 的名称，仅用于留痕，不是身份认证；没有提供名字时记为 `user:unnamed`，界面显示「未署名」 |
| 访问控制 | 一类扩展点。插件在请求进入时识别是谁并决定是否放行，识别出的名字作为执行者；内核已接好，第一期没有带这样的插件 |
| 设计对象 | 用一份说明文档代表的一个设计主题，例如“宝箱”，其他资产通过归属关系指向它 |
| 四视图 | 一张完整的图片资产，按固定格子排布同一个物体的几个视图，不拆成多个文件 |
| 格子信息 | 四视图分成几行几列、每一格是哪个视图，记在元数据文件的 `views` 里；程序按它取出对应的视图，不根据长相识别 |
| 附属文件 | 单独没有意义、只被其他资产引用的文件，例如 glTF 的 `.bin` |
| 提示条 | 界面右下角弹出的通知类小浮层，报错、提示、操作结果都用它 |
