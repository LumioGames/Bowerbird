# Review 提示词

把下面整段交给负责 review 的 Agent（或人）。它适用于两个时间点：工程搭建前（拿原型对照设计文档，评估怎么实现）和工程搭建后（再加上对照代码）。

```text
你要对 Bowerbird 做一次实现前后的对照审查。Bowerbird 是一个开源、网页版的游戏资产管理器（TypeScript 全栈，Node.js + SQLite，React + three.js 网页外壳，pnpm 单代码库）。仓库根目录即本项目。

审查的依据是一份已经评审过的高保真交互原型。你的任务是回答六个问题：程序怎么实现、哪些要进一步优化、哪些程序做不到或代价过高、哪些信息是冗余的、哪些没做好、哪些是框架有但原型没设计的。只出报告，不改任何文件。

【先读这些，按顺序】
1. design/README.md：原型与设计系统的说明、怎么打开、两份开发参考。
2. .spec/AGENTS.md、.spec/knowledge/README.md：项目是什么、知识导航。
3. .spec/knowledge/features/ 下全部文档，从 overview.md 读起；.spec/decisions/ 下全部 ADR（Accepted 的视为约束，除非你明确建议新增一条取代它）。
4. design/docs/deviations.md（原型相对提示词改了什么、为什么）、design/docs/pages.md（页面与状态）、design/docs/components.md（组件与变体，哪些只在原型里）、design/docs/copy.md（文案）。
5. .workflow-drafts/wf-20261125-bowerbird-phase1/prototype-prompts.md：原型的原始需求。
6. 两份开发参考，必须实际读：
   - Magic UI：https://github.com/magicuidesign/magicui
   - Apple 设计技能：https://github.com/emilkowalski/skills/blob/main/skills/apple-design/SKILL.md
7. 如果工程已经搭建：读 .spec/knowledge/features/engineering.md 定的包划分，再读对应代码。

【必须亲自操作原型】
在浏览器打开 design/prototype/index.html（3D 需要联网加载 three.js）。左下角「图层」按钮是评审专用控制：切换空资产库、加载中、连接失败；四条演示路径；有无版本插件。至少走完：
- 演示路径 1–4（校验 Agent 登记的原画、从模型追溯到原画并对比、复制被引用的资产、外部删除后重新定位）；
- 对比页的每一种组合（图片、视频、音频、模型、文本、模型对照四视图）和每一种方式；
- 3D 查看器的通道分量、顶点色组、卷帘、尺寸与比例尺、出图；
- 版本页签有插件 / 无插件两种形态、恢复与撤销；
- 设置里的插件、标签、任务、本机（含局域网警告）。
原型里的示意性数据（如固定的面数、合成的问题）不算需求；界面结构、状态、文案、交互规则算需求。判断不了的，写进报告的「待确认」。

【六个问题，逐项回答】

A. 怎么实现
- 按 engineering.md 的包划分，说明每个页面、每个组件落在哪个包（内核、外壳、哪个插件），需要哪些接口（对照 api-and-agent.md，缺的端点写出来）、哪些索引字段、哪些后台任务阶段。
- 原型是命令式 HTML，程序用 React：指出哪些原型写法不能照搬（全局状态、直接改 DOM、内联模板），应该怎样拆组件和管理状态。
- 动效与组件风格以 Magic UI 和 Apple 设计技能为准：逐项说明原型里的动效（弹簧、可打断、惯性、橡皮筋、FLIP、从指针处展开）在 React 里用什么实现；Magic UI 里哪些组件可以直接用、哪些要改、哪些不该用（例如过度装饰、与「文字少、只留关键信息」冲突的）。
- 3D：three.js 版本、加载器（GLB/glTF/FBX/OBJ）、通道分量的着色器做法、顶点色多组的读取、包围盒与比例尺、出图、渲染工作者（浏览器后台生成缩略图）怎么落地。

B. 需要进一步优化的
- 规模：一万到十万个资产时的网格虚拟化、缩略图加载、搜索、关系图节点数、完整性页条目数。
- 性能：大图像素差异、大模型加载、多个 WebGL 上下文（对比页、版本预览、校验队列同时存在时）。
- 体验：键盘路径、焦点管理、撤销的一致性、空 / 加载 / 出错状态是否齐全、深浅色对比度（design/tools/check.mjs 已知 2 处偏低）、窄屏。
- 无障碍与国际化：读屏、快捷键的 Windows 对应、文案可翻译。

C. 程序做不到或代价过高的
逐条给出：原型里的哪个行为、为什么做不到或很贵（浏览器限制、格式解析、跨平台、性能）、替代方案、是否需要改设计文档。至少检查：
- 「用默认程序打开源文件」「在文件夹中显示源文件」在浏览器里的可行性（服务与浏览器同机时的实现、不同机时怎么办）；
- 四视图自动识别在非纯色背景、贴得很近、带大量标注文字时的可靠性；匹配度怎么算才有意义；
- 浏览器内逐像素差异对 8K、16K 图片的代价；
- FBX 等格式在浏览器里读取顶点色、多组 UV、骨骼的可行性；
- 版本内容快照、恢复写新版本、历史关系图对版本插件（Lore、Git LFS）的要求；
- 后台渲染依赖「有浏览器页面开着」的可靠性；
- 云盘同步冲突副本的检测。

D. 冗余、没必要的资产信息与内容信息
- 检查器、详情页、对比页的技术信息表、校验页签、校验队列之间重复展示的字段；同一信息出现多次是否必要。
- 对美术和 Agent 都没有决策价值的字段（例如对所有资产都相同的值、只在原型里为了好看加的统计）。
- 违反「文字少、只留关键信息」的说明文字、提示、占位文本。
- 只为评审存在的控件（左下角「图层」按钮）不进产品。
- 数据模型层面：哪些字段可以派生而不必存（对照 data-model.md、library-format.md 的「磁盘为唯一真值，索引可重建」）。

E. 没做好的
- 页面之间同一操作的名称、图标、位置、快捷键不一致的地方；对话框按钮顺序与主次；三组状态标记（阶段、校验、问题）的表达是否处处一致。
- 文案：逐条对照 design/docs/copy.md，挑出不了解内部机制的美术看不懂的。
- 边界情况：撤销后的状态、并发修改（两个人同时改标签、扫描中删除）、长名称、超多标签、空值。
- 原型与 .spec 文档自相矛盾的地方（文档回写已覆盖评审决定，但可能有遗漏）。

F. 框架有、原型没设计的
逐个对照 .spec/knowledge/features/ 的每一节，列出有功能但原型没有界面或流程的。至少检查：Agent 接入（HTTP API、事件流、MCP、命令行、执行者留痕在界面上的呈现）、搜索（语义检索、文本语法、结果融合与排序的界面）、智能文件夹的编辑、插件扩展点（每类扩展点在界面上的插槽是否都有示意）、任务管线的各阶段、扫描对账的各条规则（文件改名、移动、外部修改）、版本插件（Lore、Git LFS）的同步状态、多资产库与首次使用、导出、模板 / 团队规范定制、通知与事件。

【报告格式】
写到 design/review/{日期}-review.md（只新建这一个文件，不改其他文件），中文：
1. 结论：一段话，最重要的三件事。
2. 六个部分 A–F，每条发现一行，表格列：编号（A-01…）、位置（页面 / 组件 / 文档章节，能给文件和行号就给）、现象与证据（怎么复现、看到什么）、影响、建议、优先级（P0 阻塞实现 / P1 影响体验或一致性 / P2 可以以后做）、归属（内核 / 外壳 / 某个插件 / 设计文档 / 设计系统）。
3. 「待确认」：需要产品决定的问题，每条给出你的倾向和理由。
4. 建议的后续工作：按优先级排的前十项，每项写清楚产出物。

【原则】
- 每一条都要有证据：原型里的操作步骤、文档的章节、或代码位置。没验证过的写「未验证」，不要猜。
- 遵守项目定下的原则：内核不认识任何文件格式、AI 服务或版本控制系统（都做成插件）；磁盘上的资产库文件夹是唯一真值，索引与缓存可重建；内核不做登录与权限；流程尽量不要人工步骤，自动结果给出可信度（ADR-013）。建议违反这些原则时，必须明确说明并给出理由。
- 不要因为原型里「做出来了」就默认程序也该这样做；也不要因为实现难就删掉评审已定的需求（design/docs/deviations.md 第一类），而是给出可行的替代。
```
