# ADR-068：写入信息时说出想要的结果，内核只写有差别的部分

状态：Accepted
日期：2026-11-27

## 背景

- 现在每次写入都是一个动作，例如「给这个文件加一条出处」。动作执行两次，就写两遍。
- 动作的结果取决于执行前是什么样、执行了几次。一次真实项目接入的使用反馈（2026-11-27）里因此出现：
  - 不敢重跑登记脚本，怕记录写两遍；`--on-conflict skip` 对库里已有的文件不起作用，照样写了一条新记录；
  - 没法先试一下，一试就真写了；
  - 89 张图各有各的提示词和来源，只能循环调 89 次命令；
  - 批量登记、试运行、重跑不重复，被当成三项各自要补的功能。

## 决策

**写法**
- 写入「算不出来的信息」（[ADR-067](ADR-067-bmeta-only-for-what-cannot-be-recomputed.md)）时，请求说的是想要的结果，例如「这个文件的出处是照某张图出的，工具是某某，提示词是某某」，不说要执行的动作。
- 内核拿想要的结果和现在的样子比，只写有差别的部分。同一份请求再说一次，没有差别，什么都不写。
- 标签、关系这类成组的信息，按「有这一项」「没有这一项」来说，不整组替换。两个人同时改同一个资产时互不覆盖，与 ADR-038 一致。

**由此得到的三种用法**
- **批量**：一份清单，每行写一个文件想要的结果，各带各的来源、出处、标签和阶段。
- **试运行**：只比不写，列出每个文件改之前是什么、改之后是什么。
- **重跑**：安全，没有差别就不写。

**哪些仍然是动作**
- 上传、移动、改名、删除、替换文件内容、从回收站恢复。它们改的是文件本身，不是关于文件的信息，保持原样。
- 上传时同名怎么办（`onConflict`）只属于上传这个动作；对库里已有的文件写信息时没有这个参数。

**各个入口**
- 界面、命令行、MCP 都只负责拼出「想要的结果」交给内核。比较与写入的逻辑只有内核里一份。

## 替代方案与否决理由

- **保留动作式写入，逐项补功能**：给重复登记加去重、给命令加试运行开关、另做一个批量清单。每一项都要单独实现和测试，而且以后每加一种写入都要再补一遍这三样。
- **整份替换**（请求给出资产的全部信息，内核整份覆盖）：最简单，但调用方必须先读出全部信息再写回，两个调用方同时写会互相覆盖。

## 兼容影响

- 改口 [ADR-051](ADR-051-reconcile-and-trash-details.md) 的「通过路径登记已认领的文件」：那一段定的是逐个字段的合并办法（标签取并集、`origin` 只在原来为空时写等），改为按本条比较后只写差别。
- knowledge/features/api-and-agent.md：
  - `POST /assets` 带 `path` 的就地登记、修改单个资产信息、`POST /assets/batch` 里改信息的部分，改为同一种「想要的结果」请求；
  - 上传与其余动作的端点不变；
  - MCP 工具与命令行跟着改。
- knowledge/features/plugin-system.md：插件登记产出时走的是同一种请求（ADR-016 第 2 条的「一条入库的路」不变，请求的形式跟着变）。
- knowledge/features/web-shell.md：检查器与批量修改提交的内容。
- packages/schema、packages/core 的登记与修改、packages/cli、packages/mcp、packages/web 的调用处。

## 实现时要定的

- 「想要的结果」的具体结构，以及清单文件的格式（反馈建议每行一个 JSON）。
- 试运行结果的结构。[ADR-072](ADR-072-no-undo-list-by-last-modifier.md) 依赖它带有「改之前」的值。
- 清单里一部分成功、一部分失败时怎么回报。
